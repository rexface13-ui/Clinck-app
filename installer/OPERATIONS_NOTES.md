# ملاحظات تشغيلية — من جلسة إصلاح جهاز عيادة "كريستال"

كتبتها بعد جلسة تصحيح طويلة على نسخة deploy فعلية شغّالة (`YousefClinic`).
الهدف: أي تحديث جاي يوصل الجهاز ده (أو أي جهاز زبون تاني) يعدّي من غير
ما يكرر نفس المشاكل. موجّهة لأي حد/مساعد ذكاء اصطناعي شغال على
`Clinck-app` (ريبو التطوير الرئيسي).

## 1. Migration لازم تتشغّل مع كل تحديث — بدون استثناء

لقينا migration فعلية (`add_receives_full_report_to_telegram_links`) كانت
موجودة بالكود من التزام (commit) قديم، لكن محدش شغّل `php artisan migrate`
بعد سحبها — فالعمود ما كانش موجود بقاعدة البيانات، وأي محاولة حفظ من
الواجهة كانت بترجع خطأ صامت (الفرونت إند كان بيعمل optimistic update
فبيبين إنه اشتغل، لكن فعلياً بيرجع القيمة القديمة).

**القاعدة:** `installer/update.ps1` و`SystemUpdateController.php` أصلاً
بيشغّلوا `artisan migrate --force` تلقائياً كخطوة 3 — **المشكلة صارت
لأننا (كمساعد) تدخّلنا يدوياً بـ `git reset --hard` + `composer install`
منفصلين عن السكربت الرسمي أثناء الدباجة (debugging)، فتخطّينا خطوة
الـ migrate.** أي تدخّل يدوي مستقبلي المفروض يشغّل نفس خطوات
`update.ps1` بالكامل بالترتيب، مش خطوات مجتزأة.

## 2. كل endpoint جديد بالباك إند لازم يترافق بواجهته بنفس الالتزام

لقينا **ميزتين كاملتين بالباك إند بدون أي واجهة مقابلة**:
- زر "إغلاق المحل" (`POST /reports/close-day`) — مش موجود بالداشبورد خالص.
- مفتاح "التقرير الكامل" للطبيب (`PUT .../full-report`) — الـ API بيرجّع
  الحقل، لكن صفحة تيليغرام ما كانت بتعرضه ولا فيها toggle له.

كمان لقينا endpoints تانية أقدم بنفس الوضع (`service-categories` CRUD،
`services/{id}/branch-prices`، `telegram-registrations/{id}/link-staff`
لربط موظف — مش بس طبيب/مريض، و`purchase-invoices/{id}/lines/bulk`
لإدخال أصناف بالجملة). دول موجودين بس ما استُخدموش بعد — قرار نكملهم
ولا لأ يرجع للمطوّر.

**القاعدة:** قبل أي commit فيه controller/route جديد، تأكد إن فيه صفحة أو
زر فعلي بالفرونت إند بيستخدمه، أو سجّله صراحة كـ "backend جاهز، frontend
لسه" بمكان واضح (TODO.md مثلاً) بدل ما يضيع.

## 3. `frontend/dist` مش متتبّع بـ Git — لازم قرار واعي

`frontend/.gitignore` بيستبعد `dist` (صح لريبو التطوير `Clinck-app`، غلط
لريبو توزيع زبون زي `YousefClinic`). فلمّا ريبو الزبون اترفع أول مرة بنسخة
كاملة من `Clinck-app` (مع نفس `.gitignore`)، أي `git reset --hard` بعدها
كان بيمسح `frontend/dist` الموجودة محلياً بدون ما يعوّضها — شاشة بيضاء.

**الحل المطبّق مؤقتاً:**
- `update.ps1` و`SystemUpdateController.php` دلوقتي بياخدوا نسخة احتياطية
  من `frontend/dist` (وكمان `php83/`) قبل أي `reset --hard`، ويرجّعوها لو
  انمسحت ولم تتعوّض من الريبو.
- ثبّتنا Node.js على هالجهاز (`winget install OpenJS.NodeJS.LTS`) كحل
  بديل، بحيث نقدر نبني `frontend/dist` محلياً وقت الحاجة.

**الحل الصح طويل المدى (قرارك):** إما (أ) `git add -f frontend/dist` عند
كل push لريبو زبون [الطريقة المتبعة حالياً — راجع `installer/DEV_MACHINE_PROMPT.md`]،
أو (ب) تثبيت Node.js كجزء رسمي من حزمة التوزيع (زي `php83/`) وإضافة
`npm run build` كخطوة تلقائية داخل `update.ps1`/`SystemUpdateController`
نفسهم بعد كل `git pull` — كده أي جهاز زبون يبني نسخته لحاله دايماً ومفيش
اعتماد على تذكّر المطوّر يعمل force-add في كل push.

## 4. تسجيل الدخول بقى بـ username مش email

آخر تحديث غيّر `LoginController` من email-based لـ username-based
(case-insensitive على `username` column). أي توثيق قديم أو رسائل ترحيب
تتكلم عن "البريد الإلكتروني" لتسجيل الدخول بقت غير دقيقة.

## 5. QUEUE_CONNECTION=redis لكن مفيش Redis شغال

`.env` مضبوط على `QUEUE_CONNECTION=redis`، لكن مفيش Redis server شغال
على جهاز الزبون هذا أصلاً. لو أي كود مستقبلي استخدم `dispatch()` لجوب
حقيقي (queued job)، هيتراكم بصمت ومحدش هيعالجه. إما (أ) شغّل Redis
فعلياً + أضف `queue:work` كنافذة رابعة بـ`start.ps1` (زي `telegram:poll`)،
أو (ب) بدّل `QUEUE_CONNECTION` لـ `sync` لو مفيش خطط فعلية لاستخدام queue
قريباً.

## 6. أداء "إغلاق المحل" (`closeDay`) هيتباطأ مع الوقت

`DailyReportService::buildSessionsLogHtml()` بيعيد بناء سجل **كل** جلسات
العيادة من أول يوم، وبيرفعه كامل عالـ GitHub Contents API، **في كل ضغطة
على زر إغلاق المحل** — مش بس اليوم الحالي. مع نمو البيانات (349+ فاتورة
لحد هلق بعيادة وحدة)، الوقت هيزيد تدريجياً. يستاهل مراجعة: إما تقييد
السجل لفترة معيّنة (آخر سنة مثلاً)، أو حفظ نسخة incremental بدل إعادة
البناء الكامل كل مرة.

## 7. الفرق بين ريبو التطوير وريبو الزبون

- `Clinck-app` = ريبو التطوير الرئيسي (فيه `frontend/src` الكامل، `build.bat`).
- `YousefClinic` (وأي ريبو زبون تاني) = قناة توزيع فقط. لما تُنشأ لأول
  مرة، لازم تُنشأ من ناتج `build.bat` (نسخة `DentaFlow-deploy` جاهزة)،
  **مش نسخة خام من `Clinck-app`** — وإلا بيرجع نفس مشكلة `dist` المفقود.

راجع `installer/DEV_MACHINE_PROMPT.md` بنفس المجلد لتفاصيل خطوات الرفع
اليومية (force-add لـ dist، إلخ).
